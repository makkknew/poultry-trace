# Poultry Trace

Веб-приложение для учета партий птицы и передач между этапами **Инкубация → Взращивание → Убой → Упаковка**. Данные хранятся в PostgreSQL, вход проверяется сервером, а производственные события сохраняются в журнале с проверяемой SHA-256 hash chain.

## Быстрый запуск в Windows

1. Установите **Docker Desktop** и откройте его. Дождитесь, пока Docker Desktop покажет, что движок запущен.
2. Откройте папку `poultry-trace` в Проводнике и дважды нажмите **«Запустить Poultry Trace.bat»**. При первом запуске Docker загрузит базовые образы и соберет приложение; это может занять несколько минут.
3. Когда в окне появится адрес, откройте [http://localhost:8080](http://localhost:8080).
4. Войдите, например, как `manager`. Временный пароль берется из `SEED_DEMO_PASSWORD` в `.env`; при первом входе система предлагает сменить пароль.
5. Чтобы остановить приложение, дважды нажмите **«Остановить Poultry Trace.bat»**. Ваши данные останутся в локальном томе базы.

При первом запуске файл `.env` создается автоматически из `.env.example`. Эти значения предназначены для локальной демонстрации. Для рабочего использования сначала замените `POSTGRES_PASSWORD`, `JWT_SECRET`, `JWT_REFRESH_SECRET` и `SEED_DEMO_PASSWORD` в `.env` на собственные случайные значения. Секреты не сохраняются во frontend и файл `.env` исключен из Git.

## Демо-аккаунты

Все 14 учетных записей создаются при первом старте. У них общий временный пароль из `SEED_DEMO_PASSWORD` в `.env` и включено требование смены пароля.

| Этап / доступ | Логины |
|---|---|
| Инкубация | `inc_op1`, `inc_op2`, `inc_lead` |
| Взращивание | `grow_op1`, `grow_op2`, `grow_lead` |
| Убой | `slaughter_op1`, `slaughter_op2`, `slaughter_lead` |
| Упаковка | `pack_op1`, `pack_op2`, `pack_lead` |
| Все этапы | `manager` |
| Полный доступ | `admin` |

Первые два пользователя этапа имеют роль оператора, третий — старшего смены. Публичная регистрация выключена. `ADMIN` создает учетные записи и блокирует их; `MANAGER` может читать пользователей и производственные отчеты.

## Что входит

- React, TypeScript и Vite frontend; FastAPI, Pydantic и SQLAlchemy backend; PostgreSQL 16 и Alembic.
- JWT access token и ротируемая refresh-сессия в HttpOnly cookie. Пароли хэшируются Argon2.
- Защита входа от перебора, временная блокировка и нейтральное сообщение при неверных учетных данных.
- Роли `OPERATOR`, `SHIFT_LEAD`, `MANAGER`, `ADMIN`; сервер проверяет роль и производственный этап для каждого запроса.
- Партии, последовательные передачи только на следующий этап, приемка с автоматическим подсчетом расхождения и подтверждение старшим смены.
- Потери с порогом подтверждения, проверкой доступного количества и обязательным комментарием для причины «Другое».
- Ручные корректировки баланса проходят двойное подтверждение; автор запроса не может подтвердить свою корректировку.
- Остаток считается сервером по начальным количествам, подтвержденным приемкам, отправкам, одобренным потерям и корректировкам. Отправить или списать сверх доступного остатка нельзя.
- In-app уведомления, dashboard по этапам, первые зарегистрированные расхождения, alerts и аналитика.
- CSV, XLSX и PDF экспорт партий, передач, потерь, расхождений и аудита для `MANAGER`/`ADMIN`.
- Аудит действий с актором, временем, IP, user agent и request ID. Хэш-цепочка проверяется через страницу журнала; PostgreSQL trigger запрещает UPDATE/DELETE строк аудита обычной учетной записи приложения.
- JSON-логи запросов, защитные HTTP-заголовки, CORS и ограничение частоты входа.
- Идемпотентный seed с четырьмя демонстрационными партиями: две передачи с расхождениями (2 и 5 голов), одна без расхождения и одна ожидающая приемки.

## Этапы производства и права

Переход назад или через этап запрещен. Передача списывается с остатка отправляющего этапа после отправки. Полученное количество добавляется принимающему этапу после подтверждения старшим смены. Если отправлено и принято разное количество, до подтверждения требуется объяснение. Подтвержденную операцию нельзя отредактировать; для исправления создается отдельная корректировка, которую подтверждает другой старший смены.

Операторы видят данные своего этапа. Старший смены видит свой этап и подтверждает приемки, крупные потери и корректировки. Руководитель видит отчеты по всем этапам, но не меняет производственные записи. Администратор управляет учетными записями.

## Проверка проекта

При установленном Docker выполните в папке проекта:

```powershell
docker compose run --rm backend pytest -q
docker compose run --rm frontend npm run build
docker compose run --rm frontend npm test
```

Backend-автотесты проверяют неверный вход и блокировку, серверный RBAC, создание партии, запрет превышения остатка, передачу 200 → 198, комментарий к расхождению, подтверждение старшим смены, запрет повторного подтверждения, разделение обязанностей при потерях и валидность цепочки аудита. UI-тесты проверяют отправку формы входа и показ серверной ошибки; production-сборка frontend включает проверку TypeScript.

API документация после запуска: [http://localhost:8080/api/docs](http://localhost:8080/api/docs).

## Развертывание frontend на Netlify

В репозитории уже есть `netlify.toml` и Netlify Function, которая проксирует `/api/*` к FastAPI. Поэтому frontend и HttpOnly refresh-cookie работают с одного домена. Для FastAPI добавлен `render.yaml`, подготовленный для бесплатного демо-сервиса на Render. PostgreSQL размещается отдельно; Netlify публикует frontend и прокси, а не заменяет backend или базу.

1. Загрузите папку проекта в GitHub и подключите репозиторий к Netlify как новый сайт. Netlify автоматически возьмет настройки из `netlify.toml`: базовая папка `frontend`, команда `npm run build`, папка публикации `dist`.
2. Создайте PostgreSQL проект на Neon Free и Web Service на Render из Blueprint `render.yaml`. В Render задайте `DATABASE_URL` — скопируйте строку подключения Neon целиком. Приложение автоматически выберет установленный psycopg-драйвер. Render сам сгенерирует `JWT_SECRET`, `JWT_REFRESH_SECRET` и временный пароль для демо-аккаунтов. Сначала проверьте публичный адрес API, например `https://poultry-trace-api.onrender.com/health`.
3. В настройках сайта Netlify откройте **Project configuration → Environment variables** и добавьте `API_ORIGIN` со значением публичного адреса backend без завершающего `/` (например `https://api.example.com`). Пересоберите сайт.
4. В переменных окружения backend задайте production `DATABASE_URL`, `JWT_SECRET`, `JWT_REFRESH_SECRET`, `SEED_DEMO_PASSWORD`, `ENVIRONMENT=production` и `CORS_ORIGINS` с Netlify URL. Используйте случайные секреты, не коммитьте `.env` и проверьте, что backend выдает HTTPS.
5. Откройте адрес сайта Netlify. Для входа используйте seed-аккаунт и временный пароль, заданный на backend.

Функция Netlify возвращает ошибку 503, если `API_ORIGIN` не задан, и 502, если backend недоступен; она не содержит фиктивной авторизации и не хранит бизнес-данные. При смене переменной на Netlify требуется новый deploy. Значение `API_ORIGIN` задается в Netlify UI/CLI, а не в `netlify.toml`.

**Ограничения бесплатного демо:** Render Free засыпает после 15 минут без запросов, поэтому первый запрос может ждать около минуты. Neon Free масштабирует БД до нуля и ограничивает вычисления/хранилище; это подходит для знакомства и проверки, но не для рабочих производственных данных. Не используйте этот бесплатный профиль как постоянную систему учета.

## Резервная копия PostgreSQL

После запуска проекта откройте PowerShell в папке `poultry-trace` и выполните:

```powershell
.\scripts\backup.ps1
```

Файл появится в `backups`. Чтобы восстановить его, выполните:

```powershell
.\scripts\restore.ps1 -BackupFile .\backups\ИМЯ_ФАЙЛА.dump
```

Восстановление перезаписывает текущую базу. Перед этим сохраните актуальную резервную копию.

## Структура папок

- `backend/app` — API, конфигурация, модели данных, безопасность и бизнес-правила.
- `backend/alembic` — схема и миграции базы данных.
- `backend/tests` — автоматические проверки критических операций.
- `frontend/src` — интерфейс пользователя.
- `scripts` — резервное копирование и восстановление.
- `docker-compose.yml` — запуск PostgreSQL, API и веб-интерфейса.
- `netlify.toml` и `frontend/netlify/functions/api-proxy.mts` — публикация SPA и безопасный same-origin proxy на Netlify.

## Ограничения текущей версии

- Docker Desktop не входит в проект. Для запуска контейнеров он должен быть установлен и запущен на компьютере.
- Email-провайдер не настроен. Публичный `/auth/forgot-password` возвращает нейтральный ответ, а `/auth/reset-password` сообщает, что доставка сброса не настроена. Администратор может выдать временный пароль через экран пользователей; пользователь обязан сменить его при входе.
- Offline очередь операций и автоматическая синхронизация после восстановления сети не включены. Сервер остается единственным источником истины; интерфейс требует соединения с API.
- PDF создается стандартным шрифтом ReportLab. Для русских шрифтов при экспорте с кириллицей нужно добавить и лицензировать TTF-шрифт.
- In-memory ограничитель попыток входа рассчитан на один backend процесс. При горизонтальном масштабировании его нужно перенести в Redis.
- Этот MVP не прошел внешний security audit и нагрузочное тестирование; локальная проверка не означает готовность к промышленной эксплуатации.

## Production перед внедрением

Настройте TLS reverse proxy, сложные уникальные секреты и ротацию, резервное копирование по расписанию с проверкой восстановления, централизованные логи/алерты и Redis для ограничения частоты. Добавьте доставку сброса пароля, полноценную проверку браузерных E2E сценариев, шрифты PDF и операционные политики для смен. Проведите независимое тестирование прав доступа и конкурентных операций на реальном PostgreSQL.
